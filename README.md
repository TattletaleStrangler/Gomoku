# Гомоку (5 в ряд) — Android-приложение на Kotlin

Нативное Android-приложение для игры в гомоку: **офлайн против компьютера** и
**онлайн 1-на-1 по коду комнаты** (сервер — проект `Backend/`, `TZ_BACKEND.md`).
Доска всегда **15×15**. Офлайн-сложность выбирает движок: **Сложный** — движок
**Rapfi** (протокол Gomocup/Piskvork), **Нормальный** — встроенный AI (итеративное
углубление + альфа-бета). Если Rapfi недоступен, сложный уровень откатывается на
встроенный AI и помечает это в шапке.

Реализовано по техническому заданию `TZ_GOMOKU.md`.
Отличие от ТЗ §3 (F-01): поддержка 13×13 и 19×19 убрана — игра идёт только на
15×15, а встроенный AI предлагается как отдельный уровень сложности.
Идентификатор приложения: **`com.oldmermaidman.gomoku`**.

Лицензия — **GPL-3.0-or-later** (см. [§14](#14-лицензия) и
[`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md)).

## 3. Сборка

1. Установите **JDK 17** (проект собран и проверен на Corretto 17) и **Android
   Studio**. Для `compileSdk = 37` нужна установленная платформа **API 37**
   (`SDK Manager → SDK Platforms`), а также build-tools и NDK — для сборки движка.
2. Укажите SDK в `local.properties` (`sdk.dir=...`) — файл не хранится в git.
3. В Android Studio: **Gradle JDK = 17** (`Settings → Build Tools → Gradle`).
   Более новые JVM (21/25) для Gradle 9.6 не подходят.
4. Сборка из командной строки:

```bash
./gradlew assembleDebug     # → app/build/outputs/apk/debug/app-debug.apk
./gradlew bundleRelease     # → app/build/outputs/bundle/release/app-release.aab (для Play)
./gradlew lintDebug         # статический анализ
./gradlew testDebugUnitTest # JVM-тесты встроенного движка
```

Обёртка `gradlew` входит в репозиторий и использует Gradle 9.6.0.

Адрес сервера задаётся типом сборки: **debug** — `http://10.0.2.2:8080` (эмулятор),
**release** — заглушка `https://api.gomoku.invalid` до появления домена. Другой адрес
передаётся без правки исходников:

```bash
./gradlew assembleDebug -Pgomoku.apiBaseUrl=http://127.0.0.1:8080
```

Второй вариант нужен физическому устройству: `adb reverse tcp:8080 tcp:8080`
пробрасывает порт телефона на компьютер, и `127.0.0.1` внутри приложения — это уже
сервер. Открытый HTTP разрешён **только в debug** (`src/debug/AndroidManifest.xml`).

## 4. Интеграция движка Rapfi

Android 10+ (API 29) запрещает `exec()` файлов из `filesDir` (политика W^X),
поэтому движок размещён в двух местах:

- **Бинарник:** `jniLibs/arm64-v8a/librapfi.so`. Упаковывается как нативная
  библиотека, ОС распаковывает его в `nativeLibraryDir` — единственное место, где
  `exec()` разрешён (`packaging.jniLibs.useLegacyPackaging = true`). `chmod` не нужен.
- **Данные (config + веса):** `assets/engine/`. `NativeExe` рекурсивно копирует их
  в `filesDir/engine/`, и этот каталог становится рабочим для процесса — Rapfi
  находит конфиг и веса рядом. Структура и подробности — в
  [`assets/engine/README.md`](app/src/main/assets/engine/README.md).

### Самопроверка (ТЗ §4.1)

1. `START 15` → ожидается `OK` (читаются все строки до `OK`, движок может печатать баннер);
2. `BEGIN` → ожидается ход с корректной координатой.

Только после успеха `available = true`. При любой ошибке сложный уровень
откатывается на встроенный AI, и шапка помечает это как
«Сложность: Сложный · встроенный»; причина пишется в logcat (тег
`RapfiGomokuEngine`).

### Сложность и движок

| Сложность | Движок | Бюджет на ход |
|---|---|---|
| Нормальный | встроенный AI (`BuiltInAI`) | 1,5 с |
| Сложный | Rapfi; при недоступности — встроенный AI | 5 с (Rapfi) / 3 с (резерв) |

Шапка показывает **сложность**, а не имя движка: по ней и так понятно, кто играет.
Пометка «· встроенный» появляется только при откате, чтобы подмена сильного
движка не осталась незамеченной.

### Протокол Gomocup/Piskvork (ТЗ §4.2)

| Направление | Команда | Описание |
|---|---|---|
| приложение → движок | `START 15` | инициализация |
| движок → приложение | `OK` | подтверждение |
| приложение → движок | `INFO rule 0` / `INFO rule 4` | freestyle / рендзю |
| приложение → движок | `INFO game_type 0`, `INFO timeout_turn <мс>` | тип соперника и бюджет времени |
| приложение → движок | `BEGIN` | первый ход движка (пустая доска) |
| приложение → движок | `BOARD` + `x,y,field` + `DONE` | состояние доски |
| движок → приложение | `x,y` | ход движка |
| приложение → движок | `END` | завершение партии |

`field` = **1** для камня AI, **2** для камня соперника.

**Две неочевидные особенности Rapfi**, обнаруженные при отладке (см.
`Rapfi/command/gomocup.cpp`):

1. **Порядок камней в `BOARD` важен.** `getPosition()` определяет свой цвет по
   *первому* камню списка (`selfColor = side == SELF ? BLACK : WHITE`) и затем
   переигрывает позицию, считая первый ход чёрным. Если отправлять камни в порядке
   координат, движок выбирает не тот цвет и завершает разбор позиции **без вывода
   хода** — это выглядит как зависание. Поэтому камни отправляются **в порядке
   ходов**.
2. **Нумерация правил у Rapfi своя:** `0` = freestyle, `1` = standard,
   `4` = рендзю, `5` = freestyle+swap1, `6` = freestyle+swap2. Рендзю — это **4**,
   а не 5, как в «сыром» битмаске протокола.
3. **`INFO timeout_turn` обязателен.** Без него Rapfi ищет со своим бюджетом по
   умолчанию, который может превысить таймаут чтения ответа.

### Таймауты и перезапуск (ТЗ §4.3)

Чтение ответа идёт с таймаутом (12 с) через отдельный поток с
`LinkedBlockingQueue`. Каждый запрос хода выполняется в **свежем процессе**
(`START` → `BEGIN`/`BOARD`): это исключает рассинхронизацию состояния. При
таймауте или некорректном ходе процесс уничтожается (`END` → `destroy` →
`destroyForcibly`), запрос повторяется один раз; при повторной неудаче движок
помечается недоступным. В `onCleared` ViewModel процесс завершается принудительно.

## 5. Соглашение о координатах (ТЗ §4.4)

- Координаты **нумеруются с нуля**: `(0,0)` — левый верхний угол, `(7,7)` — центр
  доски 15×15, диапазон `0..14`.
- При разборе ответа движка берётся **последняя** строка с допустимой координатой:
  перед ходом Rapfi может выводить служебные строки (`MESSAGE`, `DEBUG`, …).
  Это исправляет баг «смещения ходов» из эталонной реализации `peilian-qipan`.
- `coord_conversion_mode = "none"` в `config.toml` — координаты движка совпадают
  с экранными без отражений.
- Для ручной проверки позиций есть скрипт
  [`tools/test_rapfi_adb.ps1`](tools/test_rapfi_adb.ps1) (запускает бинарник на
  устройстве через `adb shell` + `run-as` и прогоняет три сценария).

## 6. Встроенный AI (ТЗ §5)

`BuiltInAI` — один самодостаточный класс без внешних зависимостей. Он играет
**уровень «Нормальный»** и служит резервом для «Сложного», если Rapfi недоступен.

Порядок работы:

1. **Лестница форсированных ходов** — до поиска разрешаются ситуации, где ход не
   вопрос оценки: выиграть, закрыть пять, сделать открытую четвёрку, закрыть
   открытую четвёрку соперника. Последний пункт — это и есть «закрыть тройку»:
   берётся клетка, на которой соперник создал бы открытую четвёрку.
2. **Итеративное углубление + alpha-beta с PVS** над транспозиционной таблицей
   (2¹⁸ записей, Zobrist-хеширование), с killer/history-упорядочиванием.
3. **Форсированный quiescence** — на горизонте рассматриваются только форсирующие
   ходы; если соперник грозит пятью, допустимы только закрывающие.
4. **Оконная оценка** — каждое окно из 5 клеток оценивается по числу камней одного
   цвета, поэтому разрывные фигуры (`XX.X`, `X.XX`, `X.X.X`) видны так же, как
   сплошные ряды. Оценка «по длине подряд идущего ряда» их не видела.

Ходы, создающие или закрывающие четвёрку, никогда не отбрасываются обрезкой списка
кандидатов. Null-move pruning намеренно **не** используется: в гомоку «пропуск хода»
никогда не безопасен, и он давал неверные отсечения.

Бюджет времени: **1,5 с** на «Нормальном» и **3 с**, когда встроенный AI подменяет
собой недоступный Rapfi на «Сложном». Для ориентира: на открытой позиции 15×15
движок доходит до **глубины 7** (≈570 тыс. узлов) за 3 с.

При включённых запрещённых ходах запрещённые ходы чёрных исключаются и из лестницы,
и из поиска.

Поведение зафиксировано регрессионными тестами
(`app/src/test/java/com/oldmermaidman/gomoku/engine/BuiltInAITest.kt`): закрытие
открытой тройки (в том числе на плотной доске), закрытие разрывной четвёрки,
взятие своей победы, приоритет открытой четвёрки над закрытием чужой тройки,
соблюдение бюджета времени.

## 7. Правила

- Победа: **пять камней в ряд** по горизонтали, вертикали или диагонали.
- При включённой опции «Запрещённые ходы чёрных» для чёрных действуют правила
  рендзю: **overline** (6 и более в ряд), **четыре-четыре**, **три-три** —
  поражение. Проверяется и ход человека, и ход AI. Пятёрка имеет приоритет над
  4-4 / 3-3 (это победа, а не запрет).
- Отмена хода снимает один полный раунд (ход AI + ход игрока), вплоть до пустой
  доски — критерий приёмки № 7.

## 8. Сохранение состояния и поворот экрана

- Позиция сериализуется в `SharedPreferences` после каждого хода
  (`GomokuGame.encode()/decode()`: размер, цвет игрока, флаг запретов, победитель,
  флаг окончания, флаг проигрыша по времени, история ходов). Формат помечен `V2`:
  партия, сохранённая сборкой без часов, читается по-прежнему. Состояние, сохранённое
  старой версией с доской другого размера, отбрасывается — поддерживается только 15×15.
- Настройки (цвет, сложность, режим игры, тема, номера ходов, запреты, звук) —
  отдельные ключи. Остаток времени на часах хранится рядом с ними и переживает
  перезапуск.
- **Ориентация не заблокирована** (Android 16+ игнорирует фиксированную ориентацию
  на больших экранах), а `configChanges` не даёт Activity пересоздаваться; состояние
  всё равно переживает сворачивание и убийство процесса.

## 9. История партии

Отдельный экран (`HistoryActivity`) — по той же причине, что и настройки: модальных
окон в игре нет. Открывается кнопкой с часами в шапке главного экрана.

- **Список ходов**: «12. ● H8 чёрные» — номер, камень, клетка и сторона. Клетки
  именуются `A`..`O` по столбцам и `1`..`15` по строкам, счёт от левого верхнего
  угла, поэтому центр доски — `H8` (`Coordinates`). Номер строки совпадает с
  номером на камне, если в настройках включены номера ходов. Ход, на котором партия
  стоит сейчас, выделен акцентом.
- **Просмотр**: тап по ходу показывает позицию после него на доске-предпросмотре.
  Копию позиции строит `GomokuGame.positionAfter(n)`, живая партия при просмотре не
  меняется; префикс короче полной истории никогда не считается законченным, потому
  что настоящая партия шла дальше, а полная история переносит свой результат
  (победу с линией, ничью, фол, сдачу) как есть.
- **Откат**: кнопка «Продолжить с этого хода» возвращает число сохраняемых ходов в
  `MainActivity`, а `GomokuViewModel.rollbackTo(n)` обрезает партию
  (`GomokuGame.rollbackTo(n)`), снимает результат вместе со статистикой, сохраняет
  состояние и, если ход за компьютером, сразу запускает его. Незавершённый расчёт ИИ
  для отброшенной позиции отменяется.

Кнопка «Отмена» — частный случай отката: она снимает один полный раунд и реализована
через тот же `rollbackTo`.

## 10. Таймер и режим игры

Режим игры выбирается на экране настроек: **Без таймера** (casual) или один из трёх
контролей. Часы только у человека — у движка свой бюджет на ход, просрочить он не
может, — и идут они только пока ход за человеком.

| Режим | Основное время | Инкремент | Сумма по FIDE |
|---|---|---|---|
| Классика | 30 мин | +30 с | 60 мин → классика |
| Рапид | 15 мин | +10 с | 25 мин → рапид |
| Блиц | 3 мин | +2 с | 5 мин → блиц |

FIDE классифицирует контроль по `основное время + 60 × инкремент`: не меньше 60
минут — классика, от 10 до 60 — рапид, не больше 10 — блиц. Рапид 15+10 и блиц 3+2 —
официальные контроли чемпионатов мира FIDE, поэтому взяты как есть. Классика опущена
с 90 до 30 минут: на доске 15×15 её основное время не тратится никогда, и режим не
отличался бы от «Без таймера». Значения заданы в `TimeControl`, а тест
`GameClockTest.presetsFallIntoTheFideClassTheyAreNamedAfter` следит, чтобы названия
режимов не разошлись с формулой.

Как это работает:

- **Инкремент** начисляется после каждого хода человека, включая первый — как в FIDE.
- **Просрочка — поражение**: `GomokuGame.timeExpired()` отдаёт партию компьютеру, в
  строке статуса «Время вышло — победил компьютер», в статистику идёт поражение.
- **Часы стоят, пока думает компьютер** и пока экран не на виду: время в фоне не
  считается, остаток сохраняется и восстанавливается после сворачивания и убийства
  процесса.
- **Отмена хода и откат** снимают инкременты отменённых ходов (иначе «ход — отмена —
  ход» бесконечно набирал бы время), но партию, проигранную по времени, не отменяют:
  часы не отматываются, и кнопка «Отмена» в этом случае заблокирована.
- **Смена режима** в середине партии даёт текущей партии новые часы с полным основным
  временем; «Новая игра» — тоже.

Время считает `GameClock`: он ничего не измеряет сам, а получает монотонное время
аргументом (`SystemClock.elapsedRealtime()`), поэтому не зависит от Android, не
боится перевода системных часов и не «догоняет» время, пока приложение свёрнуто.
В шапке часы показываются как `mm:ss` с округлением вверх, а в последние 10 секунд
окрашиваются в цвет `timeLow` темы.

## 11. Журнал сбоев

Приложение не отправляет крэши никуда само: журнал — это просто папка с текстовыми
файлами в приватном хранилище (`filesDir/crashes`). Разрешение `INTERNET` нужно
только онлайн-разделу, и журнал им не пользуется.
Отчёт покидает устройство только тогда, когда игрок сам нажмёт «Отправить» и выберет
приложение в системном окне «Поделиться».

Как это устроено:

- `GomokuApp` при старте ставит свой `Thread.UncaughtExceptionHandler` (`CrashHandler`)
  и **передаёт исключение прежнему обработчику** — системному, так что обычный отчёт о
  падении никуда не пропадает;
- `CrashReport.format()` собирает текст: время, версия сборки (`BuildConfig`), модель
  устройства и версия Android, имя потока и стектрейс со всеми `Caused by`. Отчёт
  обрезается на 32 000 символов;
- `CrashStore` пишет по файлу на сбой (`crash-<время>.txt`, UTF-8), держит **не больше
  10** записей (цикл падений не забьёт хранилище), читает журнал целиком, считает
  записи и очищает его. Посторонние файлы в папке не трогаются;
- ошибка при записи отчёта глушится: сбой журнала не должен подменять исходное
  исключение.

Экран — `CrashLogActivity`, открывается из настроек кнопкой «Журнал сбоев (N)» с числом
записей: моноширинный текст всех отчётов, кнопки «Отправить» (системный `ACTION_SEND`),
«Очистить» (с подтверждением) и «Закрыть». Пустой журнал показывает пояснение вместо
текста.

Формат и хранилище не зависят от Android и покрыты JVM-тестами (`CrashReportTest`,
`CrashStoreTest`): заголовок, цепочка причин, обрезка длинного отчёта, порядок «сначала
новые», предел в 10 записей, очистка и неприкосновенность посторонних файлов.

## 12. Локализация RU/EN

Строк два набора, и **язык по умолчанию — английский**:

| Каталог | Язык | Роль |
|---|---|---|
| `res/values/` | английский | по умолчанию: на него откатывается любая локаль, для которой перевода нет |
| `res/values-ru/` | русский | перевод |

Порядок выбран сознательно: устройство с локалью, которой приложение не знает
(немецкая, испанская), получает английский текст, а не русский. Для Android 13+ есть
`res/xml/locales_config.xml` (`en`, `ru`) и `android:localeConfig` в манифесте — это
даёт выбор языка приложения в системных настройках; на более старых версиях атрибут
игнорируется, поэтому у него стоит `tools:targetApi="33"`.

Правила:

- ни одной пользовательской строки в коде и разметке — только `@string`/`getString`;
- ключи двух файлов обязаны совпадать, за этим следит lint (`MissingTranslation`);
  совпадение подстановок (`%1$s` и т. п.) lint не проверяет — его стоит сверять вручную
  при правке строк (в текущих наборах 162 ключа и полное совпадение подстановок);
- добавить третий язык = скопировать `values/strings.xml` в `values-<код>/`, перевести
  и дописать локаль в `locales_config.xml`.

## 18. Онлайн-игра

Онлайн-часть работает поверх бэкенда `Backend/` (`TZ_BACKEND.md`): команды идут по
REST, WebSocket только уведомляет. Истина о партии — на сервере: клиент отправляет
намерение и заменяет свою копию тем снимком, который вернул сервер.

### Экраны

| Экран | Что делает |
|---|---|
| `AccountActivity` | вход и регистрация, профиль со счётом, выход, удаление аккаунта (с подтверждением паролем) |
| `OnlineActivity` | создание комнаты (правило + контроль времени), вход по коду, ожидание соперника с кодом на экране, «вернуться в партию» |
| `OnlineGameActivity` | доска (`BoardView` переиспользуется), часы обоих игроков, статус, сдача, отмена хода |

Вход в раздел — иконка «Онлайн» в шапке главного экрана. Если игрок не вошёл,
открывается экран аккаунта; после входа — комнаты.

### Сетевой слой (`net/`)

- `ApiClient` — REST на OkHttp: регистрация, вход, refresh, комнаты, ходы, сдача,
  отмена. `401` — один автоматический refresh и повтор; отклонённый refresh
  выбрасывает токены и возвращает игрока на вход.
- `TokenStore` — access/refresh в отдельном файле `gomoku_auth`, исключённом из
  резервного копирования; access обновляется за минуту до истечения.
- `GameSocket` — WebSocket `/ws/game` с заголовком `Authorization`. Сервер не
  отвечает на protocol-level ping, поэтому клиент шлёт текстовый `PING` раз в 10 с
  (сервер отвечает `PONG`); без этого простаивающее соединение сбрасывалось.
  Переподключение — с backoff (1, 2, 4, 8, 16, далее 30 с); `GAME_STATE` на каждое
  подключение лечит состояние после разрыва.
- `RemoteClock` — чистый класс: остаток из снимка плюс локальный монотонный отсчёт;
  часы устройства не используются.
- `ApiError` — код сервера → строка `strings.xml` (RU/EN); неизвестный код
  показывается как «Что-то пошло не так», а не сырым текстом.

### Отмена хода (FEATURES.md)

- кнопка «Отмена (N)» показывает остаток попыток; запрос возможен только в первые
  две секунды после **своего** хода (точное окно проверяет сервер);
- кнопка активна только у того, кто только что походил: после хода соперника она
  гаснет и снова включается после следующего своего хода; при нуле попыток остаётся
  видимой, но неактивной;
- если ответ REST приходит после события сокета, экран всё равно снимает флаг
  «команда в полёте» — иначе кнопка залипала бы выключенной (исправленный баг);
- соперник видит над доской панель «Соперник просит отменить ход» с «Да» / «Нет» и
  обратным отсчётом; запросивший видит ту же панель без кнопок;
- принятая отмена снимает камень; запросивший видит на его месте полупрозрачный
  призрак, пока не походит снова;
- часы отвечающего на время запроса стоят; время, потраченное запросившим, не
  возвращается; попытка расходуется и при отказе;
- причина отказа не показывается — только короткая вспышка «Одобрено» / «Отказано».

Панель — часть разметки экрана, а не системный диалог: правило «в игре нет модальных
окон» сохраняется.

### Проверка на стенде

Стенд поднимается `docker compose up --build` в `Backend/`. Эмулятор видит его по
`http://10.0.2.2:8080`; телефон — через `adb reverse tcp:8080 tcp:8080` и сборку с
`-Pgomoku.apiBaseUrl=http://127.0.0.1:8080`. Сценарий приёмки: два аккаунта, комната
по коду, серия ходов, сдача, отмена и переподключение. Пошаговая инструкция —
[`TESTING_ONLINE.md`](TESTING_ONLINE.md).
